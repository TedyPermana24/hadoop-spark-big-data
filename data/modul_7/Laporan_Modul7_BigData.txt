1	Pendahuluan
Modul ini membahas konsep dan implementasi pemrosesan data terstruktur dan semi-terstruktur berskala besar menggunakan modul Apache Spark SQL dan abstraksi DataFrame. Pembahasan mencakup peranan Spark SQL dalam ekosistem Apache Spark, perbedaan fundamental antara RDD tingkat rendah tanpa skema (untyped) dan DataFrame tingkat tinggi yang memiliki representasi tabular berstruktur skema (typed/schema-aware), pemuatan serta transformasi data terdistribusi (filter, groupBy, agregasi), registrasi temporary view untuk mengeksekusi kueri ANSI SQL terdistribusi, serta penyimpanan keluaran ke dalam format penyimpanan kolumnar terkompresi (Apache Parquet). Modul ini juga mendalami mekanisme optimasi kueri otomatis melalui Catalyst Optimizer (penyusunan Logical Plan, Optimized Logical Plan berbasis Predicate Pushdown dan Column Pruning, serta Cost-Based Physical Plan) dan akselerasi komputasi berbasis Tungsten Execution Engine (whole-stage code generation dan off-heap memory management). Seluruh konsep tersebut kemudian diimplementasikan ke dalam studi kasus kesehatan integrasi data multi-format pasca-akuisisi jaringan rumah sakit—menyatukan rekaman medis relasional (CSV) dan data admisi semi-terstruktur berbasis standar HL7/FHIR (JSON) guna menganalisis tren kunjungan IGD, tingkat readmisi 30-hari per departemen, serta penanganan schema evolution yang disajikan secara interaktif melalui Serving Dashboard.

Alur kerja Spark SQL berpusat pada optimalisasi pemrosesan data terstruktur melalui Catalyst Optimizer dan Tungsten Engine. Ketika data dibaca ke dalam DataFrame, Spark membentuk skema data yang terdefinisi. Kueri deklaratif (baik melalui DataFrame API maupun sintaks SQL) terlebih dahulu diterjemahkan ke dalam bentuk Unresolved Logical Plan, divalidasi skemanya melalui Catalog menjadi Logical Plan, lalu dioptimasi oleh Catalyst Optimizer menggunakan serangkaian aturan transformasi seperti Predicate Pushdown (mendorong filter ke lapisan pembacaan data) dan Column Pruning (hanya memproyeksikan atribut yang diperlukan). Rencana logis yang telah dioptimalkan kemudian dikonversi menjadi satu atau lebih Physical Plan, di mana rencana fisik dengan estimasi biaya komputasi terendah dipilih dan dieksekusi oleh Tungsten Engine menggunakan teknik whole-stage code generation untuk menghasilkan bytecode JVM yang sangat efisien di dalam memori RAM.

3	Studi Kasus Kesehatan (Health Informatics Case Study)
Integrasi sistem rumah sakit pasca-akuisisi dan merger antar fasilitas kesehatan menghadapi tantangan heterogenitas format data rekam medis. Untuk menganalisis pola alur pelayanan pasien (patient flows) secara komprehensif, data harus diintegrasikan dari sumber terstruktur (tabel relasional EHR dalam format CSV) dan semi-terstruktur (format standar pertukaran klinis HL7/FHIR Encounter dalam format JSON) tanpa downtime migrasi skema. Untuk memenuhi kebutuhan tersebut, diterapkan arsitektur pemrosesan Big Data modern:
1.	Hadoop Distributed File System (HDFS) untuk penyimpanan terdistribusi dataset rekam medis pasien (EHR) dan arsip log admisi semi-terstruktur FHIR JSON.
2.	Apache Spark SQL Engine untuk memuat data multi-format ke dalam DataFrame, menyatukan relasional CSV dengan FHIR JSON melalui operasi JOIN, serta mengoptimalkan eksekusi kueri menggunakan Catalyst Optimizer dan Tungsten Engine.
3.	Serving Layer Dashboard untuk menyajikan visualisasi tren admisi harian, profil readmisi per instalasi, serta korelasi klinis secara terpadu bagi klinisi dan manajemen rumah sakit.

1.	Menyiapkan dan Menyimpan Data Admisi FHIR dan Rekam Medis ke HDFS
Tahap pertama adalah menyiapkan berkas admisi pasien berstandar FHIR Encounter (fhir_admissions.json) yang memuat 801 data kunjungan pasien dengan atribut semi-terstruktur (encounter_id, patient_id, admission_date, day_of_week, department, length_of_stay_days, readmission_30d, serta atribut evolusi klinik baru seperti acquired_clinic_code, triage_score_mews, dan hl7_message_id) serta dataset rekam medis klinis (full_dataset_ehr.csv) yang memuat 10.000 riwayat pasien lengkap dengan diagnosa penyakit dan profil tanda vital. Kedua berkas tersebut diunggah dan disimpan ke repositori HDFS pada direktori '/hospital/spark_sql/'.

2.	Analisis Tren Admisi Pasien dan Rasio Beban IGD per Hari Menggunakan Spark SQL
Tahap ini bertujuan mengidentifikasi pola fluktuasi kedatangan pasien di seluruh jaringan rumah sakit berdasarkan hari dalam seminggu serta mengukur rasio beban Instalasi Gawat Darurat (IGD/Emergency Room). DataFrame fhir_admissions didaftarkan sebagai temporary view dan dianalisis menggunakan kueri pengelompokan GROUP BY day_of_week dengan agregasi COUNT(*) dan perhitungan persentase kasus gawat darurat.

[Gambar output hasil kueri tren admisi IGD per hari pada terminal]

Berdasarkan hasil kueri Spark SQL terhadap 801 total admisi pasien, lonjakan volume kedatangan tertinggi terjadi pada akhir pekan, yaitu hari Sabtu dengan 147 total admisi (66 kasus IGD atau 44,90%) dan hari Minggu dengan 118 total admisi (53 kasus IGD atau 44,92%). Sementara itu, proporsi kedatangan kasus gawat darurat tertinggi relatif terhadap total kunjungan harian tercatat pada hari Jumat sebesar 47,57% (49 kasus IGD dari 103 admisi) dan hari Rabu sebesar 44,21% (42 kasus IGD dari 95 admisi). Secara kumulatif, instalasi gawat darurat menangani 341 dari 801 pasien (42,57% dari seluruh penerimaan rumah sakit). Temuan kuantitatif ini menjadi dasar krusial bagi manajemen rumah sakit untuk menjadwalkan penambahan tenaga perawat dan dokter jaga pada hari Jumat hingga Minggu.

3.	Evaluasi Tingkat Readmisi 30-Hari dan Rata-rata Durasi Rawat (LOS) per Departemen
Tahap ini mengevaluasi mutu pelayanan dan efektivitas perawatan medis pasca-pemulangan pasien melalui indikator angka pasien masuk kembali dalam kurun waktu 30 hari (30-day readmission rate) serta durasi rawat inap (Length of Stay/LOS). Analisis dilakukan dengan kueri Spark SQL yang mengelompokkan data berdasarkan atribut department, menghitung frekuensi readmisi, dan mengurutkan hasilnya dari persentase tertinggi.

[Gambar output hasil kueri tingkat readmisi per departemen pada terminal]

Hasil kueri Spark SQL menunjukkan variasi signifikan antar instalasi medis:
1.	Intensive Care Unit (ICU): Memiliki tingkat readmisi tertinggi yaitu 30,36% (34 kasus readmisi dari 112 pasien) dengan rata-rata durasi rawat inap (LOS) 7,4 hari, mencerminkan tingginya komplikasi pada pasien kritis.
2.	Emergency Room (IGD): Mencatat 77 kasus readmisi dari 341 kunjungan (tingkat readmisi 22,58%) dengan rerata LOS 2,0 hari.
3.	Pulmonology Clinic: Mencatat 7 kasus readmisi dari 75 pasien (tingkat readmisi 9,33%) dengan rerata LOS 7,6 hari.
4.	Cardiology Ward: Mencatat 14 kasus readmisi dari 153 pasien (tingkat readmisi 9,15%) dengan rerata LOS 7,5 hari.

Tingginya angka readmisi pada unit ICU dan IGD mengindikasikan perlunya protokol pemulangan (discharge planning) yang lebih ketat serta pemantauan tanda vital lanjutan pasca-rawat intensif.

4.	Cross-Format Unified Join: Menghubungkan Diagnosa Relasional (CSV) dan Admisi FHIR (JSON)
Tahap ini memadukan data klinis pasien dari tabel relasional EHR (patients_ehr) dengan data riwayat admisi semi-terstruktur FHIR JSON (fhir_admissions) melalui operasi relasional JOIN terdistribusi berdasarkan patient_id. Kueri mengelompokkan data berdasarkan diagnosis (condition) dan derajat keparahan (severity) untuk mengamati korelasi profil fisiologis (tekanan darah sistolik) terhadap risiko readmisi dan durasi rawat. Tahap ini juga membuktikan keunggulan Spark SQL dalam menangani evolusi skema (schema evolution): atribut klinis baru dari klinik cabang hasil akuisisi (acquired_clinic_code, triage_score_mews, hl7_message_id) berhasil diurai ke dalam DataFrame secara toleran nilai null (null-safe dynamic inference) tanpa memerlukan alterasi skema fisik DDL (ALTER TABLE) yang berpotensi memicu kegagalan sistem. Kueri dioptimasi oleh Catalyst Optimizer melalui Predicate Pushdown dan Column Pruning (hanya memproyeksikan 7 dari 30 atribut gabungan ke memori), sehingga dieksekusi oleh Tungsten Engine dalam waktu 42,30 ms.

[Gambar output kueri cross-format join EHR dan FHIR JSON pada terminal]

Hasil penggabungan data multi-format mengidentifikasi kohort pasien berisiko paling rentan mengalami readmisi:

4.	GERD kategori Moderate (21 pasien): Mencatat tingkat readmisi 28,57% dengan rerata sistolik 141,7 mmHg dan LOS 3,4 hari.
5.	Hypertension kategori Moderate (23 pasien): Mencatat tingkat readmisi 26,09% dengan rerata sistolik 156,8 mmHg dan LOS 4,1 hari.
6.	Lung Cancer kategori Moderate (32 pasien): Mencatat tingkat readmisi 25,00% dengan rerata sistolik 142,0 mmHg dan LOS 5,1 hari.
Temuan ini membuktikan bahwa pasien gagal ginjal kronis berderajat parah dengan hipertensi sistolik tidak terkontrol merupakan kelompok paling kritis yang membutuhkan intervensi terpadu guna menekan angka rawat ulang.

1.	Rumah Sakit dan Tim Data Engineer
Mendapatkan kapabilitas integrasi data terdistribusi terpadu yang mampu menggabungkan tabel relasional CSV dan format klinis semi-terstruktur FHIR JSON tanpa hambatan ketidakcocokan skema (schema mismatch), meniadakan downtime migrasi database fisik saat sistem klinik baru diintegrasikan melalui toleransi schema evolution otomatis, mengoptimalkan kueri data skala besar melalui aturan Predicate Pushdown dan Column Pruning pada Catalyst Optimizer yang menghasilkan latensi kueri sangat rendah (42,30 ms via Tungsten Whole-Stage Code Generation), serta menyediakan antarmuka analitik siap saji berbasis REST API dan web dashboard terintegrasi.
2.	Dokter dan Tim Manajemen Operasional/Medis
Memperoleh visibilitas akurat terhadap dinamika kunjungan pasien guna mengantisipasi lonjakan beban IGD pada akhir pekan (puncak 147 kunjungan pada Sabtu dengan rasio gawat darurat mencapai 47,57% pada Jumat), mendeteksi unit pelayanan dengan kerentanan readmisi tertinggi (ICU sebesar 30,36% dan IGD sebesar 22,58%) sehingga dapat dirumuskan kebijakan pemulangan pasien yang lebih aman, serta mengidentifikasi sub-populasi pasien paling berisiko (pasien Chronic Kidney Disease stadium parah dengan tingkat rawat ulang mencapai 47,83% dan tekanan darah 168,5 mmHg) guna memberikan tata laksana preventif berkelanjutan dan meningkatkan keselamatan pasien (patient safety monitoring).
